# ZOS — V2 direction (draft, not approved)

From Zubin's 2026-11-24 framing, written up by Opus. Nothing here is
scheduled yet. `PLAN.md` is still the source of truth for what's built.

## V1: shipped

- **M9a:** routed MCP servers. Add any remote MCP with none, bearer, or
  oauth auth. Done.
- **M9b:** connector catalog. Checked-in `runtime: remote` manifests that
  can be installed from `/admin`; nothing installed by default. Done.
- **M9c:** async approvals. Approval-tier calls from clients without
  elicitation (phones) are approved in `/admin`. Done.

## North star (Zubin, 2026-11-24): the V3–V9 shape

- **Distribution.** Each person gets their own ZOS. They click a button and
  it deploys to infrastructure they own. Every deployment is personal;
  there's no multi-tenant SaaS.
- **Modules.** Modules are installable from /admin, like early WordPress
  plugins. Installing one spins up its service:
  - **Chat:** a small Slack that agents post into and Zubin can read.
  - **Whiteboard:** a persistent whiteboard the user controls, which agents
    can read and draw on.
  - **Google:** Gmail, Calendar, and the rest.
  - **Photo library**, and so on.
- **Authoring.** There's a clean, infrastructure-agnostic way to write
  modules, so Claude Code can write new ones.
- **Every agent sees the same layer.** OpenClaw, Claude Code, Codex,
  ChatGPT, Muse, and Instinct all reach the same installed modules.
- **Connector.** MCP is the connector layer, and that's enough for now. A
  CLI or a bearer/OAuth API could be added later if distribution needs it.

ZOS is the **core plane**: auth, policy, routing, audit, the module
lifecycle, and the shell UI. Everything else is a module.

## The model: the employee and their workplace

Think of an employee. They have a **brain** (intelligence) and **hands**
(dexterity). A good employee writes down what they know instead of keeping it
in their head. So everything they work *on* and *with* lives outside them:
- notes and documentation
- chat with colleagues
- tickets and documents
- the apps and services they use
- designs and physical goods

| Employee | Agent world | Who owns it |
|---|---|---|
| Brain | the LLM | not ZOS |
| Hands | the harness (Claude Code, Codex, ChatGPT, …) | not ZOS |
| Everything they work on and with | ZOS | **ZOS** |

**ZOS is the OS layer that lets those things exist.** It is the traveling
pocketbook of Zubin's domain, handed to whichever agent he uses. It never
touches the brain or the hands. We don't measure ZOS by how smart or capable
an agent is. We measure it by whether Zubin's domain is complete, correct,
and reachable from every agent he uses.

What goes into the domain spans a wide range:
- **Simple:** notes, memories, files.
- **Middle:** full hosted applications (front end, back end, database)
  in a particular format, e.g. Cloudflare apps.
- **Rich:** a chat service. Agents sign in ("I'm X, Zubin uses me for Y"),
  post, and ask "what messages are there for me?"

Some of these exist elsewhere already (Gmail, Calendar, the Mac), and ZOS
routes to them. Others don't exist yet, and ZOS hosts them. **The job of ZOS
is to support all of these.**

### Consequences for design

- **ZOS core models the domain, not agents.**
  - A client is a *door with a key*: it handles auth, policy, and
    attribution.
  - An agent's identity and role ("I'm Muse, I do X") is *content inside a
    service*, such as the chat service's directory or a memory. It is not a
    core concept.
- **Cross-agent continuity is a side effect, not the goal.** If app
  hosting exists, every agent sees the same apps, because the apps live in
  the domain.
- **Agents are trusted to do their own work.** Syncing skills to disk,
  caching, and rendering in the harness are agent-side work.
- **Push** (a message pushed into an agent) is a real service feature
  with an asterisk. It means delivering into hands ZOS doesn't own.
  Deferred, but not ruled out on principle.

## Decided (Zubin, 2026-11-24)

- Agents connect as separate clients.
- ZOS is the canonical source for skills; agents sync them to disk.
- File stores: whatever file-store provider is added becomes the canonical
  one.
- These are conceptual layers, not things to nail down today.

## Modules: the unit of everything

**A module is an MCP server plus a manifest, run by ZOS.** The core sits in
front of every module and supplies auth, policy, routing, and audit. A
module never sees client tokens. This takes the M5 upstream proxy and makes
it the universal path: first-party and Claude-written modules alike are
just MCP servers behind the core, in any language.

**Manifest:**
- name, version, and description
- a tool prefix, with a tier for each tool
- runtime: a container or process image, or `remote: <url>` for a routed
  service such as Google's MCP
- storage requests: a Postgres schema, a blob prefix. The core provisions
  these and hands them in as env.
- config and secrets schema, plus an optional OAuth connect flow (how
  Google onboarding generalizes)
- optional **human UI**: routes the core mounts behind owner auth, e.g. the
  chat room or the whiteboard canvas. This is the user's view of their own
  services, not an agent UI.
- optional device half: an actuator binary that dials in, as the Mac
  daemon does today

**Lifecycle in /admin:** install, configure, connect, enable or disable,
upgrade, and uninstall. Every step is audited. Disabling hides the
module's tools and keeps its data.

**Where things move:**
- Memory becomes a module.
- gcal and gmail become the Google module.
- The actuator becomes the Mac module's device half.
- Where a backend varies by person, a module keeps one tool surface and
  swaps backends, as gcal `api|mcp` does today. For apps, Zubin's
  Cloudflare and a friend's Fly are both backends.

**The fork to decide later: the module runtime is the hosting target.**
- On the laptop, modules are docker compose services.
- On Cloudflare, they would naturally be Workers dispatched per module.
  This is the shape Workers for Platforms is built for.

"Click a button to deploy your ZOS" depends on this choice, so make it
together with the ZOS-hosting decision. Nothing today blocks either path,
as long as modules are only ever reached over MCP.

**Rendering UI inside chat clients.** The MCP Apps extension lets a
module's UI (whiteboard, chat) render inside ChatGPT or Claude. It's
spec-native, so it fits "MCP is enough."

## Candidate services

- **App hosting.** This is the clearest case of a service that only makes
  sense inside the domain. The app, its versions, its backend, its
  visibility, and its preview in /admin all belong together.
  - Tools: `apps_publish/list/versions/rollback/unpublish`. The host is a
    swappable backend, Cloudflare Workers first.
  - Policy: `apps_publish` is `external` tier.
  - Visibility: private by default.
- **Chat.** Replaces the "channels-as-buffer" spike.
  - Agents sign in and keep a directory entry (who they are, what Zubin uses
    them for).
  - Channels and DMs: `chat_post`, and `chat_read` with a cursor.
  - Queues for work to burn down: `chat_claim`, `chat_ack`.
  - Push is deferred (see above).
- **Skills.** Canonical SKILL.md files: `skills_list/get`, plus MCP
  prompts/resources. Agents sync them.
- **Files.** Whatever file-store provider is plugged in. Artifacts are files
  rendered in /admin.
