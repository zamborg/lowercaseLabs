# 01: System Contract

This document defines non-negotiable platform rules for all app repos generated by coding agents.

## 1. Runtime Model

- Apps run as single-tenant pods on Fly Machines.
- Pod isolation is infrastructure-level, not application-level multi-tenancy.
- App code should not assume a global shared database across users.

## 2. Networking Modes

### Proxy Mode

- Pod is private/internal.
- Client traffic flows through Data Plane.
- Data Plane validates JWT and uses `fly-replay`.
- Recommended default for most apps.

### Direct Mode

- Pod can be reached via public Anycast IP.
- Client gets direct route via Control Plane route-resolution endpoint.
- Use only when bandwidth/latency profile requires direct path.

## 3. App Contract

Every submitted app repository must include:

- `Dockerfile`
- `fly.toml`
- Application process that listens on one HTTP port

`fly.toml` must include:

- `app = "<fly-app-name>"`
- `[metadata] networking_mode = "proxy" | "direct"`
- `internal_port` in either `[http_service]` or `[[services]]`

## 4. Environment Variables Passed By Platform

Platform provisioning injects:

- `POD_ID`
- `POD_OWNER_ID`
- `APP_MODE`

Generated applications should treat these as read-only runtime metadata.

## 5. Security Expectations

- Trust boundary: Data Plane does auth in Proxy mode.
- Do not disable HTTPS assumptions in production configs.
- Do not hardcode secrets in source.
- Support runtime env configuration for API keys and service credentials.

## 6. Data Expectations

If persistent state is needed:

- App should read/write from a local mount path (for example `/data`).
- Keep schema migration path deterministic and startup-safe.

## 7. Compatibility Target

A compliant generated app should be ingestible with:

1. `POST /apps/charts/parse`
2. `POST /apps/from-chart`

And operational with:

1. `POST /pods/provision`
2. `GET /pods/routing/apps/{slug}`
