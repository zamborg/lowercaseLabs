How the pieces fit

One SwiftUI app. Three runtimes behind small protocols. All state is plain files, so an external Claude Code can rewrite the fabric while the app watches.

External Claude Code works on the disk folder, not the app. The folder has its own CLAUDE.md explaining the file formats, so “add an agent called Orla who is a lighthouse keeper” is a file write, and the running app picks it up.

The agent loop, in full

protocol AgentLoop { func run(agent: Agent, history: History, tools: [Tool],
                              llm: LLM, emit: (Event) -> Void) async throws }

SimpleLoop:
  messages = system(persona + summary) + recent turns
  repeat:
    stream = llm.generate(messages, tools)       // tokens and tool calls
    emit tokens; collect tool calls
    if none: break
    run each call through ToolHub → append results
  if tokens(messages) > agent.compact_at * context: Compactor.run()

Image generation, built-in actions and external MCP tools are all just entries in ToolHub. The loop never special-cases them.

Decisions already made

Native SwiftUI, not Open WebUIOpen WebUI is a Python and Svelte web server in Docker. It would be the biggest dependency in the app and fights “as native as possible, super simple”. We borrow its ideas (model manager, tool mounting), not its code.
MLX for language modelsApple’s own framework and the best-supported path on Apple Silicon. Use mlx-swift-lm in process behind an actor. Weights come from mlx-community repos.
Image model in a child processZ-Image Turbo or FLUX.2 Klein via a Swift MLX port, run as a separate worker. Memory is returned to the OS when it exits, and a crash cannot take the chat down. On an M1 Max expect roughly 20–40 s per 768–1024 px image.
Downloads via swift-huggingfaceResumable snapshot downloads with a cache layout shared with Python tooling. The UI adds size, “fits in memory?” and progress.
MCP via the official Swift SDKstdio and http client, one connection per server. The app is not sandboxed so it can spawn servers. Distribute outside the App Store (Developer ID).
Files are the databaseSame call as zass. Agents are markdown with frontmatter, chats are JSONL. No SQLite. This is what lets Claude Code rewrite the fabric, and what makes pruning, export and backup trivial.
One chat per agentEnforced by the data model: chats/<agent>/. “New conversation” means prune or reset, not a second thread.
Agent loop is ~150 lines behind a protocolSwap it per agent later (ReAct, planner, none) without touching UI or runtimes.

Build plan

0 · Spike2–3 days
SwiftUI window, MLX streaming chat with one 4-bit model, one stdio MCP server (zass), full tool-call round trip.
Gate: a chosen model calls a tool correctly in 9 of 10 scripted prompts. If not, pick a different model or add constrained tool-call parsing before building anything else.
1 · Core~1 week
Swift package ParlorCore: Store (agents, chats, FSEvents reload), AgentLoop, Compactor, ToolHub, LLM actor. Plus a headless parlor-cli that drives the same core.
Gate: CLI run: create agent file → send 60 messages → compaction fires → tool call returns → history intact after relaunch. Runs in CI-style test, no UI.
2 · Chat + agents UI~1 week
Sidebar, streaming chat, tool-call chips, agent editor with live file preview, prune mode (delete, cut-after, compact now).
Gate: XCUITest drives “create Pip, chat, prune, relaunch”. Screenshots checked against these mockups.
3 · Models~4 days
HF search, resumable download, disk and memory gauge, load and unload on agent switch, fit warnings.
Gate: download a small model from scratch, interrupt, resume, assign to an agent, chat. Memory gauge matches Activity Monitor within 10%.
4 · Tool mounts~4 days
mcp.json editor, per-server status and restart, per-agent tool allowlist, tools/list_changed handling and the “tools updated” divider.
Gate: add a server while a chat is open, see the divider, next turn can call the new tool.
5 · Images~1 week
Image worker, image.generate tool, inline rendering, prompt and seed disclosure, save and copy.
Gate: “draw X” in chat → image in the log within 40 s on the M1 Max, worker memory freed after idle timeout.
6 · Make it oursongoing
Agent templates (assistant, character), import and export agent packs, folder CLAUDE.md, optional local MCP so external Claude Code can drive the app, not only its files.

Risks

  • Tool-calling quality of small local models. The biggest unknown, hence the phase 0 gate. Mitigation: pick the model for tool reliability first, keep tool lists short per agent.
  • Memory. A 17 GB language model plus a 12 GB image model fits in 64 GB, but not alongside heavy apps. The image worker unloads on idle, and the library warns before a download that will not fit.
  • Swift MLX API churn. The packages move fast. Pin versions, wrap each behind our own protocol so a change is local.
  • Swift image ports are community projects. Fallback is the Python mflux as the same worker interface, since the worker is a process boundary anyway.

How I will verify

Each gate above is run by the agent doing the work, in user-flow terms (“say draw → image appears in 24 s”), through parlor-cli and XCUITest on this Mac. Nothing is handed over as “please try it”.

Defaults I picked, tell me if wrong

  • Working name parlor, repo folder lowercaseLabs/parlor/, data in ~/parlor/.
  • macOS 26 only (this machine), Swift 6, SwiftUI with minimal AppKit.
  • Qwen3 30B-A3B 4-bit as the first assistant model, Llama 3.2 3B for characters, Z-Image Turbo for images. All swappable, they are just defaults to test with.
  • No cloud calls anywhere, including telemetry. Hugging Face downloads are the only network use.
